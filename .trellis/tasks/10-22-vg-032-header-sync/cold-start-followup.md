# 正常安装冷启动调查与已授权修复边界

用户已明确选择“授权按持久规则方案修复（推荐）”。以下初期观测和方案保留为决策依据；实现与最终验证见 implement.md 的冷启动补充记录。

2026-10-22 用户要求补齐独立配置、正常加载扩展、完整退出后重新打开的自动恢复验证。

## 已确认观察

- 有界面 Chrome for Testing 149.0.7827.55，新临时 profile，通过原生扩展管理页和文件夹选择器加载当前 dist，正常开启 Allow User Scripts。
- 退出前日语父域、法语子域的页面语言、导航及同源/跨源头一致；关闭语言子域与未匹配域均原生。
- Browser.close 正常退出，主进程和观测到的10个进程树成员全部消失，再以同一 profile 启动。没有重新加载扩展、startWorker 或管理消息。
- 冷启动首 HTTP 文档 JS 已为日语/法语，但导航及同源/跨源头仍为原生中文，首文档一致性未通过。
- 首 HTTP 之后只读采样已存在 worker：session 30000..30003 齐全、guard 已关闭、当次 session headers 报告 ok、userScripts API 可用且两条语言注册仍在；随后的新 HTTP 文档自动恢复日语/法语头。因此不是遗漏启动入口或开关丢失，而是 session 清空、异步重建与持久页面注册之间的启动窗口。调试附着发生在首失败观测之后；不能用后续收敛替代首请求成功。

早期脚本使用 JSON.stringify 比较存储配置会受对象属性顺序影响，应改用结构相等比较；不把该假差异归因于配置改变。Chrome 在未打包目录生成 _metadata 索引，资产一致性核对需排除这个浏览器管理目录，不能误称源码被修改。

## 需要改变的合同

当前 AGENTS.md 和本任务 PRD 明写新请求头仅 session。仅加 onStartup、重试、延迟探针或打开管理页不能消除首请求窗口。若首文档一致性必须满足，需要将已确认请求头投影持久化，这改变了当前持久化及故障恢复保证，超出单纯补取证据。实施前取得用户对该方案的授权。

候选方案：

1. 从现有唯一有效语言 payload 生成 dynamic 持久投影；不另存语言配置。稳定且上次完整成功的冷启动直接沿用已确认投影，不在每次 worker 启动无条件打开 guard。
2. 使用独立的新 dynamic ID 范围；dynamic 30000..39999 继续为未知规则，不能因等于旧 session 范围就接管。首次接管前检查新范围已有规则，所有权不能确认则保留并隔离。旧 session 30000..39999 独立清理和读回。
3. 所有改变 header 投影的配置事务，必须在写配置前启用并读回持久 guard。否则关闭/删除站点后进程崩溃，旧 dynamic 可能在下次启动继续生效。新配置及页面、规则均确认后才解除隔离。
4. 保留默认静态升级隔离、历史1001/1002/1100..2099迁移和范围外未知冲突处理。故障时清理所属投影并保持隔离；不放宽 host、verified 或页面注册边界。
5. 真实正常UI验证稳定冷启动首文档、关闭/删除事务中断后重启、Allow User Scripts 关闭后冷启动、重新启用与旧session迁移，并独立只读复核。

dynamic 也不能使 userScripts 与 DNR 跨API原子一致；特别是用户脚本开关改变、扩展更新或故障期间，不承诺后台核验前所有请求一致。回退包需先清理新所有者的 dynamic 规则，不能直接降级并忽略残留。

该方案已在获得单独授权后实施；修复前session-only失败与修复后dynamic稳定冷启动证据分别保留，不以后台稍后收敛冒充首请求成功。
